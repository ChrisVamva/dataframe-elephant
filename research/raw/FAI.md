# Research-to-Data Capability Atlas

**Question.** How does research become structured, queryable, analyzable, visualizable knowledge — and how do skills, roles, technologies, software, companies, products, methodologies, workflows, and agents participate in the loop: Research → Evidence → Extraction → Structured representation → Normalization → Database → Query → Analysis → Visualization → Interpretation → New research → Agent iteration?

**Access date for all sources:** 2026-09-27. Evidence tags used below: `documented fact` (primary source inspected), `reported signal` (secondary/multi-source but not independently verified), `inference` (our synthesis), `recommendation` (our judgment).

---

## 1. Executive synthesis

- **The loop has three structurally distinct halves.** The upstream half (Research → Evidence → Extraction → Structured representation) is semantics-heavy, ill-specified, and increasingly LLM-assisted; the downstream half (Database → Query → Analysis → Visualization) is governed by decades-old, well-standardized technology (SQL, columnar engines, notebooks, BI). Normalization and data modeling are the fragile seam between the two. (`inference`)
- **Role labels are not interchangeable.** "Data analyst," "research analyst," "analytics engineer," "knowledge engineer," and "research engineer" differ in which workflow stage they own, their primary language (SQL vs. Python vs. RDF/OWL), and their outputs (reports vs. pipelines vs. ontologies). The "analytics engineer" role itself was substantially created and marketed by dbt Labs. (`documented fact` for the dbt claim — [dbt Labs](https://www.getdbt.com/blog/what-is-analytics-engineering); `inference` for the taxonomy)
- **DuckDB has collapsed the "database" stage into the analyst's process.** An in-process, dependency-free, columnar OLAP engine that queries CSV/Parquet/JSON directly removes a whole class of infrastructure work from small-to-medium research-to-data pipelines. DuckDB's ecosystem deliberately spans open source (DuckDB, DuckDB Labs) and commercial cloud (MotherDuck). (`documented fact` — [duckdb.org](https://duckdb.org/), [GitHub](https://github.com/duckdb/duckdb), [DuckDB history](https://duckdb.org/history/))
- **Provenance is the weakest-standardized stage.** W3C PROV is the mature, standard answer for "who produced what, when, from what" (`documented fact` — [W3C PROV overview](https://en.wikipedia.org/wiki/W3C_Prov), [ACM paper](https://dl.acm.org/doi/10.1145/2452376.2452478)), but it is thinly adopted in practice compared to SQL/dbt-style lineage, which only covers the downstream half. Evidence provenance for research claims (source → claim → extraction) has no dominant tooling. (`inference`)
- **LLM structured output is now the de facto extraction interface.** JSON-Schema-constrained decoding, function calling, and Pydantic/Zod validation have replaced regex-and-hope parsing for converting text to records; this is the single biggest enabler of extraction agents. (`reported signal` — [Agenta guide](https://agenta.ai/blog/the-guide-to-structured-outputs-and-function-calling-with-llms), [Towards Data Science](https://towardsdatascience.com/structured-outputs-with-llms-json-mode-function-calling-and-when-to-use-each/))
- **Agents are real at the research and extraction ends, aspirational in the middle.** Deep-research-style agents (OpenAI, Google, Azure Foundry) are shipped products; orchestration frameworks (LangGraph) provide durable execution, state, and human-in-the-loop for custom pipelines; LLM data-preparation is an active research field with known limits. (`documented fact` for shipped products — [OpenAI](https://openai.com/index/introducing-deep-research/), [LangGraph](https://www.langchain.com/langgraph); `reported signal` for research limits — [arXiv survey 2601.17058](https://arxiv.org/abs/2601.17058))
- **ETL vs. ELT is a governance decision, not a fashion choice.** ELT (load raw, transform later) preserves evidence and provenance; ETL (transform before load) enforces normalization earlier but destroys the raw record. For research workflows, ELT-like "keep the raw evidence" patterns are strongly preferable. (`documented fact` for definitions — [AWS](https://aws.amazon.com/compare/the-difference-between-etl-and-elt/); `recommendation` for the preference)
- **Open question:** no single product or methodology covers the whole loop end-to-end with claim-level provenance. The gap between "research notebook" and "queryable evidence store" is where most knowledge is lost.

## 2. Lens findings

### 2.1 Skills

- **Definition &amp; scope.** Skills are learned, transferable capabilities of humans (and, by extension, agent profiles). We distinguish: research synthesis, information extraction, data modeling, ontology design, normalization, SQL, DuckDB operation, pandas use, visualization, provenance management, and agent orchestration. These are not synonyms: SQL is a language skill; DuckDB operation is engine-specific knowledge (direct Parquet/CSV reads, in-process model); data modeling is conceptual (star schemas, fact/dim); ontology design is semantic (classes, relations, constraints in OWL/SKOS); normalization is data-hygiene (units, dates, entity resolution). (`inference`, from definitions in the sources cited below)
- **Workflow position.** Research synthesis → Research/Evidence; extraction &amp; data modeling → Extraction/Structured representation; normalization &amp; provenance → Normalization; SQL/DuckDB/pandas → Database/Query/Analysis; visualization → Visualization; orchestration → Agent iteration.
- **Representative evidence.** pandas self-describes as "open source data analysis and manipulation tool" (`documented fact` — [pandas.pydata.org](https://pandas.pydata.org/)); Polars self-describes as a Rust "analytical query engine for DataFrames" (`documented fact` — [GitHub](https://github.com/pola-rs/polars)); the analytics-engineering skill set is defined by dbt Labs as stitching ingestion (Fivetran/Stitch), warehouse tidiness, SQL transformation, and BI layering (`documented fact` — [dbt Labs](https://www.getdbt.com/blog/what-is-analytics-engineering)).
- **Trade-offs &amp; failure modes.** T-shaped profiles: deep in one stage, shallow elsewhere — the loop breaks at handoffs. Common failure: conflating ontology design (shared, reusable semantics) with ad-hoc data modeling (single-project schemas). Provenance skill is rarest and most undervalued. 
- **Confidence:** high for tool-specific skills; medium for boundary claims (data modeling vs. ontology design).

### 2.2 Market positions

- **Definition &amp; scope.** Nine commonly confused labels, separated by primary stage, language, and output:
  - **Data analyst** — Query→Analysis→Visualization; SQL + BI tools; output: reports/dashboards answering business questions. (`documented fact` — [Chartio role guide](https://chartio.com/learn/data-analytics/distinguishing-data-roles/))
  - **Research analyst** — Research→Evidence→Interpretation; domain expertise, literature/policy/evidence synthesis; output: briefs with citations, not necessarily databases. Distinct from data analysts in that the evidence base is documents, not warehouse tables. (`inference` supported by role-comparison sources)
  - **Data/BI analyst** — variant of data analyst emphasizing BI-tool ownership (Metabase/Superset/dashboard ops). 
  - **Analytics engineer** — Normalization→Database→Query; dbt/SQL; output: tested, documented transformation pipelines. This role label was popularized by dbt Labs itself. (`documented fact` — [dbt Labs](https://www.getdbt.com/blog/what-is-analytics-engineering), [LearnSQL](https://learnsql.com/blog/dbt-analytics-engineer/))
  - **Knowledge engineer / ontologist** — Structured representation; RDF/OWL, graph databases, knowledge-graph platforms. Hiring signals seen in production job posts: graph databases, ontology standards, "agentic data engineering" (`documented fact` for the posting language — [The Hartford job](https://www.jointhehartford.com/job/4647/knowledge-graph-engineer-ontologist-data-analytics-us-ct-hartford/), [Vintti template](https://www.vintti.com/job-description/knowledge-engineer)).
  - **Research engineer** — adjacent but distinct: builds research infrastructure/models (ML engineering), not primarily research synthesis.
  - **Automation specialist** — Extraction/evidence acquisition: scraping, browser automation, API integration.
  - **AI/agent workflow specialist** — Agent iteration: LLM orchestration, tool use, evaluation.
  - **Information architect** — Structured representation: taxonomy/ontology for content and knowledge systems.
- **Key non-equivalence.** Data analyst vs. knowledge engineer differ not in seniority but in representation substrate (tables vs. graphs) and in whether semantics live in code (SQL) or in explicit schemas (OWL). (`inference`)
- **Trade-offs &amp; failure modes.** Job titles are noisy: small firms attach "analyst" to engineering work. Market-signal sources (Indeed, Chartio, Research.com) are secondary and partially SEO-driven. 
- **Confidence:** medium-high (multiple independent secondary sources plus first-party job postings).

### 2.3 Technology

- **Python** — lingua franca for extraction/pandas/notebook stages. **SQL** — the query/analysis standard; DuckDB "provides a rich SQL dialect with support far beyond basic SQL" (`documented fact` — [duckdb/duckdb GitHub](https://github.com/duckdb/duckdb)). **DuckDB** — in-process, columnar, vectorized OLAP DBMS, no external dependencies (`documented fact` — [duckdb.org](https://duckdb.org/), [Wikipedia](https://en.wikipedia.org/wiki/DuckDB)); "SQLite for analytics" is a widely used characterization. **pandas** — DataFrame manipulation, in-memory, label-aligned (`documented fact` — [pandas.pydata.org](https://pandas.pydata.org/)). **Polars** — Rust, multi-threaded, SIMD, Arrow-interop, lazy query optimization; handles larger-than-RAM datasets (`documented fact` — [pola.rs](https://pola.rs/), [Polars docs](https://docs.pola.rs/)). **Notebooks (Jupyter/Observable)** — interactive compute documents; Jupyter is the open standard for Python notebooks (`documented fact` — [Project Jupyter](https://en.wikipedia.org/wiki/Project_Jupyter)); Observable is a JS-native notebook + data-app platform (`documented fact` — [observablehq.com](https://observablehq.com/)). **APIs / scraping / browser automation** — Playwright automates Chromium/Firefox/WebKit for scraping and testing (`reported signal` — [ScrapingBee tutorial](https://www.scrapingbee.com/blog/playwright-for-python-web-scraping/)). **LLMs + embeddings** — structured-output decoding for extraction; embeddings for semantic retrieval (pgvector as the "vectors inside Postgres" option) (`documented fact` for pgvector — [GitHub](https://github.com/pgvector/pgvector)). **Graph technologies** — RDF/OWL/RDFS/SKOS for ontologies (`reported signal` — [Ontology standards overview](https://medium.com/@jaywang.recsys/ontology-taxonomy-and-graph-standards-owl-rdf-rdfs-skos-052db21a6027)). **Data formats** — CSV, JSON, Parquet, Arrow (zero-copy interop per Polars docs).
- **Relationships.** Technology `implemented_by` Software; Workflow `uses` Technology.
- **Trade-offs.** pandas vs. Polars vs. DuckDB is increasingly a non-choice — DuckDB can query `SELECT * FROM 'file.csv'` directly and interop with pandas DataFrames, so hybrid stacks are common (`documented fact` — [dev.to guide](https://dev.to/emiroberti/duckdb-the-analytics-database-revolution-a-comprehensive-guide-442b), `reported signal` for its editorial framing). Failure modes: pandas memory ceilings; scraping fragility under anti-bot measures; LLM extraction schema drift.
- **Confidence:** high.

### 2.7 Methodologies

- **ETL vs. ELT.** ETL transforms before loading (stronger upfront definition, raw data destroyed); ELT loads raw and transforms in the target (uses warehouse compute, preserves originals). (`documented fact` — [AWS](https://aws.amazon.com/compare/the-difference-between-etl-and-elt/), [Rivery](https://rivery.io/blog/etl-vs-elt/))
- **Data modeling.** Structuring entities/relations/grain for queryability; dbt encodes it as version-controlled SQL with tests. Semantic data modeling has a long lineage (recognizing the need goes back to the 1970s ICAM program — `documented fact`, [Wikipedia: semantic data model](https://en.wikipedia.org/wiki/Semantic_data_model)).
- **Information extraction.** Traditionally NLP pipelines; now dominated by LLM structured output (JSON-Schema/function calling; grammar-constrained decoding). (`reported signal` — [Agenta](https://agenta.ai/blog/the-guide-to-structured-outputs-and-function-calling-with-llms), [Medium: structured output generation](https://medium.com/@emrekaratas-ai/structured-output-generation-in-llms-json-schema-and-grammar-based-decoding-6a5c58b698a6))
- **Evidence &amp; provenance systems.** W3C PROV: a family of specs (data model, XML schema, OWL2 ontology, RDF mappings) for interoperable provenance metadata — entity/activity/agent as core classes. (`documented fact` — [Wikipedia: W3C PROV](https://en.wikipedia.org/wiki/W3C_Prov), [EDBT/ACM paper](https://dl.acm.org/doi/10.1145/2452376.2452478))
- **Ontology standards.** RDF, RDFS, OWL, SKOS as the layered semantic-web stack for shared vocabularies. (`reported signal` — [standards overview](https://medium.com/@jaywang.recsys/ontology-taxonomy-and-graph-standards-owl-rdf-rdfs-skos-052db21a6027))
- **Research protocols.** Literature synthesis, systematic review, source triangulation — govern the Research→Evidence stages; largely orthogonal to the ETL family, and a boundary many teams fail to see.
- **Trade-offs &amp; failure modes.** ELT without governance becomes a raw-data swamp; ETL without provenance becomes unfalsifiable. Ontologies over-engineered for one project rarely get reused.
- **Confidence:** high for ETL/ELT and PROV; medium for LLM-extraction methodology claims.

### 2.8 Workflows

The full loop (detailed per-stage in §3). Key structural observations:

- Inputs degrade gracefully left-to-right; provenance degrades sharply. The two quality gates that matter most: **extraction validity** (does the record faithfully represent the source?) and **normalization correctness** (are units/entities/dates consistent?). (`inference`)
- Feedback loops exist at every arrow, not just the end: visualization anomalies trigger re-analysis; query errors trigger re-modeling; analysis results trigger new research. This is why agent iteration is a first-class stage, not an appendix. (`inference`)
- Historical transition: the loop used to require a data engineering team for the Database stage; DuckDB-class engines and ELT tooling let a single analyst/researcher own it. This explains the emergence of hybrid roles (analytics engineer, knowledge engineer with "agentic data engineering" expectations). (`inference` supported by [duckdb.org/history](https://duckdb.org/history/), [The Hartford posting](https://www.jointhehartford.com/job/4647/knowledge-graph-engineer-ontologist-data-analytics-us-ct-hartford/))

## 6. Research gaps and next investigations

1. **Claim-level provenance tooling** — no dominant product found that binds *source → extracted record → analytical claim*. Next: search for RO-Crate, evidence-graph systems, and qualitative-analysis tools (NVivo-class) as adjacent candidates; check dbt + PROV integration attempts.
2. **Metabase/Superset specifics** were taken from product pages not independently opened; verify feature matrices before modeling.
3. **Job-market quantification** — role distinctions rest on secondary guides and individual postings; next: systematic sampling of current job postings per role label and skill co-occurrence analysis.
4. **Google Deep Research** evidence is press-reported, not first-party; open Google's own announcement.
5. **Agent reliability numbers** — the LLM data-preparation survey ([arXiv](https://arxiv.org/abs/2601.17058)) reports task-level limits but no field failure rates for research-agent extraction pipelines; next: benchmark review.
6. **Missing categories:** data-quality monitoring tools (e.g., Great Expectations-class), qualitative research software, citation-management systems (Zotero-class), and schema-evolution governance — all plausibly belong in the atlas but were outside this pass.
7. **Falsifiability:** the "provenance whitespace" and "role non-equivalence" claims would be weakened by discovering a widely adopted claim-provenance product or evidence that employers use the role labels interchangeably in practice.

## Recommendations / next steps

1. **Model the atlas around the 12-stage workflow as the spine**, with entity tables from §4 as nodes and typed edges (`uses`, `implemented_by`, `produced_by`, `governs`, `performs`, `supports`). This keeps role labels, tools, and agents distinct while making their stage positions explicit. (`recommendation`)

3. For a concrete reference stack: DuckDB (database/query) + Parquet (storage format) + dbt-style tested SQL (normalization) + LLM structured output with Pydantic validation (extraction) + LangGraph (agent loop) + Observable or Metabase (visualization). Every component is replaceable; the workflow spine is not. (`recommendation`)
