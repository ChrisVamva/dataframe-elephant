# Export Database Protocol (ExportDatabase)

## Status

This protocol is mandatory for every person, agent, or process that exports
the production DuckDB databases into shareable file bundles. No production
database (`data/citations.duckdb`, `data/stage2.duckdb`) may be exported,
copied into a distributable form, or re-imported for verification except by
following this procedure.

---

## 1. Purpose

`data/citations.duckdb` and `data/stage2.duckdb` are the workspace's queryable
sources of truth, built per [FromStagetoDatabases.md](FromStagetoDatabases.md)
and the ingest/import pipelines. They are binary, gitignored, and not directly
readable without DuckDB. The purpose of this protocol is to:

- Define the single supported path from a production `.duckdb` file into
  restorable, human-readable file bundles, without changing the source
  database.
- Give every table a portable home in both CSV (convenient to open) and
  Parquet (typed analytical data) via DuckDB's native `EXPORT DATABASE`.
- Give every view a readable snapshot of its current query results, clearly
  labelled as a snapshot rather than a source table.
- Package each run with the context needed to trust it (inventory, run id,
  row counts, checksums, DuckDB version, restore instructions) and prove it
  restores by re-importing into a fresh temporary database.
- Feed downstream readers (spreadsheet review, external analysis, audit)
  without ever treating an export as the source of truth.

This protocol implements `Rules and Regulations/Commander Deck/Plans/ExportPlan`
(the plan file carries no extension). Core logic lives in
`src/db_export_core.py`; the thin CLI is `scripts/export_databases.py`
(mirroring the `src/*_core.py` + `scripts/` split in `AGENTS.md`).

---

## 2. Non-negotiable rules

1. **Sources of truth are fixed:** `data/citations.duckdb` and `data/stage2.duckdb`
   remain the only sources of truth. Exports under `data/exports/` are derived
   artifacts. Never edit a production database to suit an export, and never
   treat an export bundle as authoritative over the `.duckdb` file.
2. **Read-only sources:** every connection to a production database is opened
   with `read_only=True`. The exporter records the source SHA-256 and mtime
   before the run and aborts if either changed afterwards.
3. **Scope is the two production databases:** `citations` and `stage2` as
   declared in `PRODUCTION_DATABASES` (`src/db_export_core.py`). Test, scratch,
   or ad-hoc databases are out of scope unless formally promoted to production.
4. **Native export only:** table payloads are produced exclusively by DuckDB's
   `EXPORT DATABASE` (`FORMAT CSV, HEADER true` / `FORMAT PARQUET`), which emits
   restorable `schema.sql` + `load.sql` plus one file per table. Hand-rolled
   row dumping is forbidden.
5. **Snapshots are not tables:** view results are exported separately under
   `views/<db>/` via `COPY (SELECT * FROM <view>)` and must never be presented
   as source tables. Each run's `manifest.json` stores the authoritative view
   definitions (`CREATE VIEW ...` SQL); snapshot files store one moment's query
   results.
6. **No silent overwrite:** the run directory is unique per UTC timestamp
   (`export_<YYYYMMDDTHHMMSSZ>`). Refuse to write into a non-empty directory
   unless `--overwrite` is explicitly passed.
7. **Verify by default:** every bundle is re-imported with `IMPORT DATABASE`
   into a fresh temporary database and compared before the run is accepted.
   `--no-verify` is for diagnostics only; its output must not be distributed.
8. **Derived artifacts are gitignored:** never commit `data/exports/`,
   `*.duckdb`, or `*.jsonl` warning files. Each run directory carries its own
   `manifest.json` + `README.md` as the audit trail.
9. **No automatic encryption:** exports get no ECA encryption by default. If an
   encrypted archive is later wanted, follow
   [Encryption-Compression-Archiving.md](Encryption-Compression-Archiving.md)
   and its verification requirements as a separate, explicit step.
10. **DuckDB dialect only:** all SQL in tooling and bundles is DuckDB dialect.
    Do not "fix" `EXPORT` / `IMPORT` / `COPY` syntax to T-SQL.

## 3. Inputs and outputs

### 3.1 Inputs — production databases

| Name | Database | Schema | Warnings companion | Run table |
| --- | --- | --- | --- | --- |
| `citations` | `data/citations.duckdb` | `schemas/citations.sql` | `data/citation_ingestion_warnings.jsonl` | `ingestion_run` |
| `stage2` | `data/stage2.duckdb` | `schemas/stage2.sql` | `data/stage2_ingestion_warnings.jsonl` | `stage2_run` |

`schemas/*.sql` are the canonical table/view definitions (DuckDB dialect).
Warning JSONL files are the existing ingestion companions, preserved verbatim
as copies — never regenerated by the exporter.

### 3.2 Outputs — one timestamped run directory

Each run writes `data/exports/export_<UTC-timestamp>/`:

```text
data/exports/export_<UTC-timestamp>/
|-- citations_csv/            # EXPORT DATABASE bundle (FORMAT CSV)
|   |-- schema.sql            # CREATE TABLE statements (restorable)
|   |-- load.sql              # COPY ... FROM statements (restorable)
|   `-- <table>.csv           # one file per base table
|-- citations_parquet/        # EXPORT DATABASE bundle (FORMAT PARQUET)
|-- stage2_csv/
|-- stage2_parquet/
|-- views/
|   |-- citations/            # <view>.csv + <view>.parquet snapshots
|   `-- stage2/
|-- citations_warnings.jsonl  # verbatim copy of the production warnings file
|-- stage2_warnings.jsonl
|-- README.md                 # per-run layout + restore instructions
`-- manifest.json             # inventory, counts, checksums, verification
```

Partial runs (`--which citations|stage2`, `--formats csv|parquet`) produce the
corresponding subset; layout and naming are otherwise identical.

### 3.3 Manifest contract (`manifest.json`)

Sorted-key JSON containing `export_time_utc`, `duckdb_version` (verified
against DuckDB 1.5.5), `formats`, and `run_dir`; per database:
`source_database`, `source_sha256`, `run_id`, `tables`, `views`, `row_counts`
(tables plus `view:<name>` entries), `warnings_file`, `warnings_count`,
`bundles`, `view_definitions` (full `CREATE VIEW ...` SQL), `view_snapshots`,
and `source_unchanged: true`; plus `restore_instructions`, `fidelity_caveat`
(`csv_empty_string_as_null_in_nullable_columns; parquet_exact`), `verification`
(one `{"bundle": ..., "status": "VERIFIED_OK"}` per bundle, absent when
`--no-verify` was used), and `files` (`{path, size_bytes, sha256}` for every
file in the run directory).

## 4. Procedure

Run from the repo root with the repo venv (`pytest.ini` sets `pythonpath=.`).
Plain `python` may resolve to a system interpreter without `duckdb`; prefer
`.\.venv\Scripts\python.exe`.

### Step 1: Inventory and baseline (read-only)

`inventory_database()` opens the source with `read_only=True` and records:

1. Base tables from `information_schema.tables`
   (`table_schema='main' AND table_type='BASE TABLE'`).
2. User views plus their SQL from `duckdb_views()` filtered to
   `schema_name='main' AND NOT internal` — this filter is required because
   DuckDB exposes ~50 internal/temp views (`pg_*`, `sqlite_*`, `duckdb_*`)
   that must never be exported as snapshots.
3. `SELECT COUNT(*)` per table and per view (views under `view:<name>` keys).
4. The ingestion `run_id` from the run table
   (`ingestion_run` / `stage2_run`).
5. The companion warnings line count, if the JSONL file exists.

Nothing is written to the source at this step.

### Step 2: Export table bundles (native `EXPORT DATABASE`)

`export_database_bundle()` runs, still read-only:

```sql
EXPORT DATABASE '<bundle_dir>' (FORMAT CSV, HEADER true);
-- or
EXPORT DATABASE '<bundle_dir>' (FORMAT PARQUET);
```

This emits `schema.sql` + `load.sql` + one data file per table — the only
supported table payload. The run aborts with `ExportError` if either SQL file
is missing. CSV opens in spreadsheets; Parquet preserves typed data. Excel is
out of scope (needs an extension and converts types); JSON is deferred per the
ExportPlan.

### Step 3: Export view snapshots (labelled, not tables)

`export_view_snapshots()` runs one `COPY` per user view per format into
`views/<db>/`:

```sql
COPY (SELECT * FROM "<view>") TO '<dir>/<view>.csv' (HEADER, DELIMITER ',');
COPY (SELECT * FROM "<view>") TO '<dir>/<view>.parquet' (FORMAT PARQUET);
```

Snapshots are the view's query results at export time. They are never
re-imported as tables and must never be described as source tables.

### Step 4: Package context

Copy each production warnings JSONL verbatim to `<db>_warnings.jsonl`, write
the per-run `README.md` (layout, source-of-truth statement, restore snippet,
format guidance), and write `manifest.json` (§3.3) including per-file SHA-256.

### Step 5: Verify restoration and fidelity

`verify_bundle()` imports each bundle into a fresh temporary database and
checks, in order:

1. **Schema** — restored base-table set equals the inventoried set exactly;
   missing or extra tables fail the run.
2. **Contents** — `SELECT * ... ORDER BY ALL` matches the source row-for-row
   per table (CSV with the §6 normalization, Parquet exact), covering
   NULL-vs-empty, dates/timestamps, and Unicode without per-column knowledge.
3. **Views** — each restored view row count equals its inventoried
   `view:<name>` count (definitions travel inside the bundle's `schema.sql`,
   so `IMPORT DATABASE` recreates them).
4. **Foreign keys** — `PRAGMA foreign_key_check` returns no violations.
5. **Source unchanged** — source SHA-256 and mtime equal the pre-run values.

Temporary verification databases are deleted after each check.

### Step 6: Commands

```powershell
# Full export (default): both databases, both formats, verified.
.\.venv\Scripts\python.exe scripts/export_databases.py

# Subsets and options.
.\.venv\Scripts\python.exe scripts/export_databases.py --which citations
.\.venv\Scripts\python.exe scripts/export_databases.py --which stage2 --formats parquet
.\.venv\Scripts\python.exe scripts/export_databases.py --overwrite --timestamp manual-01
.\.venv\Scripts\python.exe scripts/export_databases.py --no-verify  # diagnostics only
```

```powershell
# Focused exporter tests, then the full suite (per AGENTS.md).
.\.venv\Scripts\python.exe -m pytest src/tests/test_export_databases.py -q
.\.venv\Scripts\python.exe -m pytest src/tests -q
```

## 5. Restore

Any `<db>_<format>/` directory restores into a fresh database with one
statement — no exporter code required:

```python
import duckdb
con = duckdb.connect("restored.duckdb")
con.execute("IMPORT DATABASE 'data/exports/export_<ts>/citations_parquet'")
```

`IMPORT DATABASE` recreates tables and views from `schema.sql`, then loads
table rows via `load.sql`. Snapshots under `views/<db>/` play no part in a
restore. Prefer Parquet for typed analysis and CSV for spreadsheet
inspection (mind the §6 caveat). Never restore over a production path —
restore to a new file and verify counts first.

---

## 6. Fidelity caveat (CSV vs Parquet)

DuckDB CSV semantics collapse empty strings to NULL in **nullable** columns on
roundtrip. `NOT NULL` columns roundtrip `''` faithfully, because the generated
`load.sql` uses `force_not_null` for them. Therefore:

- A CSV bundle may show `''` → `NULL` differences **only** in nullable
  columns. This is expected DuckDB behaviour, not corruption.
- `verify_bundle` normalizes exactly this case (nullable-column `''` treated
  as `NULL` on the expected side) and fails on any other difference.
- Parquet bundles preserve NULL-vs-empty exactly; no normalization applies.
- Do not "fix" a bundle by hand-editing its files — a hand-edited bundle no
  longer matches its manifest checksums and fails trust. Re-run the export.

## 7. Quality gates before an export run is complete

| Gate | Check |
| --- | --- |
| G1 Inventory | Tables, user views + definitions, row counts, run id, and warnings count all recorded; no internal views present. |
| G2 Restorability | Every bundle contains `schema.sql` + `load.sql` and re-imports into a fresh temp DB. |
| G3 Content fidelity | Full `ORDER BY ALL` row comparison passes per table (CSV normalized per §6; Parquet exact). |
| G4 View fidelity | Every restored view row count matches its inventoried `view:<name>` count. |
| G5 Referential integrity | `PRAGMA foreign_key_check` is clean in each restored bundle. |
| G6 Source preservation | Source SHA-256 and mtime unchanged; `source_unchanged: true` in the manifest. |
| G7 Auditability | Per-run `README.md` + `manifest.json` with per-file SHA-256; warnings companions copied; `data/exports/` still gitignored. |
| G8 Test suite | `src/tests/test_export_databases.py` and the full `src/tests` suite pass (modulo separately recorded pre-existing failures). |

---

## 8. What an export must not contain

| Prohibited | Reason |
| --- | --- |
| Modified production databases | Sources stay read-only; two writers drift |
| Exports presented as the source of truth | Bundles are derived snapshots; the `.duckdb` files govern |
| Internal/temp views as snapshots | Engine plumbing, not research data |
| View snapshots described as source tables | One moment's query results; definitions live in `manifest.json` |
| Hand-edited CSV/Parquet payloads | Breaks manifest checksums and verification trust |
| Committed `data/exports/` contents | Gitignored derived artifacts |
| Automatic ECA encryption of exports | Separate concern with its own passphrase/manifest lifecycle (§2 rule 9) |
| Test/scratch databases without promotion | Scope is the two documented production databases |

## 9. Failure modes and recovery

| Failure | Behaviour | Recovery |
| --- | --- | --- |
| Source database missing | `ExportError: Source database not found` before anything is written | Rebuild via `src/ingest_citations.py` / `scripts/import_stage2.py` first |
| Non-empty run dir without `--overwrite` | `ExportError: Refusing to overwrite` | Pass `--overwrite` deliberately or use a fresh `--timestamp` |
| Unknown `--which` / `--formats` value | `ExportError` listing the supported values | Re-run with `all\|citations\|stage2` and `csv,parquet` |
| Schema mismatch on verify | `ExportError: Schema mismatch` naming missing/extra tables | Inspect the bundle against `schemas/*.sql`; re-run the export, do not patch files |
| Content mismatch on verify | `ExportError: Content mismatch` naming the table and row counts | A Parquet mismatch means real drift; a CSV mismatch outside nullable-`''` is equally real |
| FK violations on verify | `ExportError: Foreign-key violations` with offending rows | Do not distribute; investigate source integrity |
| Source changed mid-run | `ExportError` naming the database | Re-run when no rebuild is in flight |
| `--no-verify` output | No `verification` entries in the manifest | Re-run without the flag before sharing |

---

## 10. Update triggers

Revise this protocol (and the exporter and tests alongside it) when:

- A third production database is declared, or a test/scratch database is
  promoted into `PRODUCTION_DATABASES`.
- `schemas/citations.sql` or `schemas/stage2.sql` gains or loses a table,
  column, or view (inventory, verification, and G1 expectations move together).
- DuckDB changes `EXPORT`/`IMPORT`/`COPY` semantics, the CSV NULL-vs-empty
  behaviour, or the `duckdb_views()` shape. The `NOT internal` filter and the
  §6 normalization are version-sensitive; both are verified against DuckDB
  1.5.5.
- A new export format (JSON, Excel, …) is approved — revisit the ExportPlan's
  deferred-format decision and §6 first.
- Encrypted export archives are approved — define the ECA hand-off as an
  explicit post-export step, not a silent default.

---

## 11. Final principle

An export is judged not by how convenient its files look, but by whether a
stranger holding only the run directory can restore every table exactly,
re-run every view definition, trace every number back to a source database and
run id, and prove the originals were never touched.
