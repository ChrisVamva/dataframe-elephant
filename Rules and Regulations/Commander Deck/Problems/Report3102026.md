## Problems

### P1 — `stage2.duckdb` and `AutomationResearch.duckdb` contain identical data (medium-high)

`data/README_database_topology.md` says `stage2.duckdb` holds **Stage 2 Extraction 1** and `AutomationResearch.duckdb` holds **Extraction 3 (Automation Market Research)**. In reality both files are byte-identical in size (8,138,752) and contain **exactly the same content**: identical row counts in every table, the same `C001` claim ("Automation is not one market; it is a stack of overlapping markets"), and the same 7 document content hashes.

That claim text exists only in `research/raw/Stage 2/Extraction 3/Claims.md` — so **both databases hold Extraction 3 data**. Extraction 1 has no database at all. Either `stage2.duckdb` was overwritten by a later Extraction-3 import, or it was copied as a starting point and never re-imported. Consequence: any notebook or script pointed at `stage2.duckdb` believing it reads Extraction 1 is silently reading the wrong extraction.

**Fix:** re-import Extraction 1 into `data/stage2.duckdb` (`scripts/import_stage2.py --stage2-dir "research/raw/Stage 2/Extraction 1" ...`), or correct the topology README if the duplication was intentional.

### P2 — `scripts/health_check.py` is broken in two ways (medium)

1. **Stale table expectations.** It checks `citations.duckdb` for `{claims, sources, metrics}`, but the actual schema (`schemas/citations.sql`) uses singular names (`claim`, `source`, `claim_source`, …) and has **no `metrics` table**. The check therefore fails every run:
   ```
   WARN: data/citations.duckdb missing tables: {'sources', 'metrics', 'claims'}
   ```
2. **Exit code never signals failure.** `main()` has no top-level return value (the `return True/False` statements live inside `check_database`), so `sys.exit(0 if main() else 1)` always exits **0** — even when a check fails. The script can never fail a CI run.

**Fix:** update expected table names to the singular schema, and make `main()` aggregate and return the overall result.
